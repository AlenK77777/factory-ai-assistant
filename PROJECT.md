# Factory AI Assistant: home lab project

> Portfolio / home-lab project. **All data is synthetic** (invented). Nothing here comes from a real company.
> Built step by step with AI-assisted development (Cursor).

## Goal

A small internal tool for a PCB manufacturing plant that covers the full cycle of an AI & automation role:
find a manual process → build a working tool in days → connect AI to company data → measure the result.

Users (shift managers, QA engineers, planners) can:

- ask an AI assistant about production orders and defects in plain language (via MCP);
- search work instructions in plain language (RAG), including fully on-premise with a local model;
- see a KPI dashboard.

## Environment

- Windows 10, PowerShell, Docker Desktop, Python 3.10+ in a venv, Git, GitHub.
- Ollama runs natively on Windows (from Step 3), on an RTX 5070 (12 GB): `qwen3-embedding:0.6b` for multilingual embeddings (1024 dimensions), `qwen3:8b` as the local chat model.
- All commands in this project are for PowerShell.

## Architecture

```mermaid
flowchart LR
    XL[Excel files] --> ING[ingest/load_excel.py<br/>validation + rejected rows]
    ING --> DB[(PostgreSQL + pgvector<br/>Docker)]
    DOCS[docs/instructions<br/>markdown files] --> IDX[rag/index_docs.py]
    IDX -->|embeddings via Ollama| DB
    CLIENT[Cursor / Claude Desktop] <--> MCP[MCP server<br/>Python, stdio]
    MCP -->|read-only role| DB
    LOCAL[rag/ask_local.py<br/>local model via Ollama] --> DB
    EMP[Browser :8443] --> NGINX[NGINX<br/>127.0.0.1 only]
    NGINX -->|host.docker.internal| CHAT[chat/server.py<br/>127.0.0.1:7777]
    CHAT <--> MCP
    CHAT -->|tool calling| OLLAMA[Ollama]
```

| Component | Where it runs | Port |
|---|---|---|
| PostgreSQL 16 + pgvector | Docker (`pgvector/pgvector:pg16`) | 5432 |
| NGINX reverse proxy (`nginx:1.28.0-alpine`) | Docker | 127.0.0.1:8088 (HTTP) and 127.0.0.1:8443 (HTTPS) → chat |
| MCP server | Windows, Python venv, stdio | none |
| Employee chat | Windows, Python venv | 7777 (127.0.0.1 only, for debugging) |
| Ollama (`qwen3-embedding:0.6b` + `qwen3:8b`) | Windows, native | 11434 |

## Design principles

- **Least privilege:** the MCP server connects with a separate read-only database role.
- **Parameterised SQL only:** never build SQL by string concatenation.
- **No secrets in git:** settings live in `.env` (git-ignored); `.env.example` has placeholders.
- **Data quality first:** every Excel row is validated; rejected rows are reported with a reason.
- **Reproducible:** the whole stack starts with `docker compose up -d`; data is regenerated by a script.
- **Grounded answers:** the assistant answers from the data and documents, and says so when it finds nothing.

## Step 1: Database and Excel ingestion (Monday)

Build:

- `docker-compose.yml` with one service `db` (image `pgvector/pgvector:pg16`), a named volume, port 5432, a healthcheck, credentials from `.env`.
- `db/init/01_schema.sql`, mounted into `/docker-entrypoint-initdb.d`: enable the `vector` extension and create the tables
  - `orders(order_id PK, customer_sector, product_type, layers, quantity, status, production_line, created_date, due_date)`
  - `defects(defect_id PK, order_id FK → orders, detected_date, station, defect_type, quantity)`
  - `ingest_runs(run_id, file_name, started_at, rows_loaded, rows_rejected)`
- `scripts/generate_data.py`: creates `data/production_orders.xlsx` (~300 orders) and `data/defects.xlsx` (~800 defects) with a fixed random seed. PCB domain values:
  - sectors: Defense, Aerospace, Medical, Industrial
  - product types: Rigid, Rigid-Flex, Flex, HDI (layer counts 2–16)
  - statuses: Planned, In Production, In QA, On Hold, Shipped
  - stations: Imaging, Etching, Lamination, Drilling, Plating, Solder Mask, AOI, Electrical Test, Final QA
  - defect types: Open, Short, Misregistration, Delamination, Plating Void, Solder Mask Defect, Drill Breakout
  - deliberately include ~10 invalid rows: missing order_id, negative quantity, unknown status, due_date before created_date, duplicate order_id, a defect that references a non-existent order.
- `ingest/load_excel.py`: reads both files (pandas + openpyxl), validates every row, loads the valid rows (idempotent: running it again creates no duplicates), writes invalid rows to `data/rejected_rows.csv` with a `reason` column, records the run in `ingest_runs`, prints a summary.
- `tests/test_validation.py`: pytest unit tests for every validation rule (no database needed).
- `requirements.txt`, `.gitignore` (`.venv`, `.env`, `__pycache__`, `data/rejected_rows.csv`), `.env.example`.

Acceptance criteria:

- [ ] `docker compose up -d db` → the container is healthy (`docker compose ps`).
- [ ] `python scripts/generate_data.py` creates both Excel files.
- [ ] `python ingest/load_excel.py` loads the valid rows and reports the rejected count; `data/rejected_rows.csv` lists every planted bad row with a clear reason.
- [ ] Running the loader a second time does not duplicate data.
- [ ] `docker compose exec db psql -U <user> -d <db> -c "SELECT status, COUNT(*) FROM orders GROUP BY status;"` returns counts.
- [ ] `pytest` passes.

## Step 2: MCP server over the database (Tuesday)

Build `mcp_server/server.py` with the official MCP Python SDK (`MCPServer`; called FastMCP before SDK v2), stdio transport.

- Connection settings come from `.env`; connect with a separate **read-only** database role.
- Log to stderr only: stdout is the MCP channel.
- Tools return structured, JSON-serialisable data, never free text:
  - `get_order_status(order_id)` → order details + number of defects; a clear error if the order does not exist.
  - `list_late_orders(as_of_date=None)` → orders past due_date that are not Shipped.
  - `defect_summary(days=30, group_by="station" | "defect_type" | "customer_sector")` → counts and share of total.
- Register the server in Cursor (`.cursor/mcp.json`); optionally also in Claude Desktop.

Acceptance criteria:

- [ ] Cursor's MCP settings show the server as connected, with 3 tools.
- [ ] In chat, "What is the status of order <id>?" calls `get_order_status`, and the answer matches the database.
- [ ] "Which station had the most defects in the last 30 days?" calls `defect_summary`.
- [ ] An unknown order id returns a clean error, not a crash.

## Step 3: RAG over work instructions (Wednesday)

- Install Ollama for Windows; pull `qwen3-embedding:0.6b` (multilingual embeddings, 1024 dimensions; chosen over `bge-m3` after a measurement on this project's EN/RU/HE questions) and the chat model `qwen3:8b` (fits the 12 GB GPU together with the embedding model).
- Write 6–8 short synthetic work instructions in `docs/instructions/*.md`: AOI false-call handling, delamination containment, ESD rules, order hold and release, electrical test failure triage, solder mask touch-up limits. Mark each file "Synthetic, for demo only".
- `rag/index_docs.py`: split into chunks (~500 characters, ~50 overlap), get embeddings from Ollama, store them in `doc_chunks(id, source, chunk_index, content, embedding vector(1024))`; re-indexing replaces the old chunks.
- Add the MCP tool `search_instructions(query, k=4)` → top-k chunks with the source file and a similarity score (cosine distance, `<=>`).

Acceptance criteria:

- [ ] `python rag/index_docs.py` reports how many chunks were stored.
- [ ] "What should I do if delamination is found?" returns chunks from the delamination instruction first.
- [ ] An unrelated question returns low-similarity results, and the assistant says it found nothing relevant.

## Step 4: Fully on-premise answer with structured output (Wednesday/Thursday)

- `rag/ask_local.py "question"`: retrieves chunks, asks the local Ollama chat model (`qwen3:8b`) to answer ONLY from those chunks, using Ollama's structured output with the schema `{ "language": "en"|"ru"|"he", "answer": str, "sources": [str], "found": bool }` (`language` is pinned to the question's script); validates the result with pydantic; retries once if the JSON is invalid.

Acceptance criteria:

- [ ] The output is always valid JSON that matches the schema.
- [ ] `sources` lists the instruction files actually used.
- [ ] For an off-topic question `found` is false and the answer says so, with no invented content.

## Step 5a: Employee web chat (before the dashboard)

A browser chat for people who do not use an IDE. `chat/server.py` listens on `127.0.0.1:7777` only. It is an MCP client of the existing factory-db server (the same 4 tools) and calls the local Ollama chat model with tool calling. The model name is `OLLAMA_CHAT_MODEL` in `.env`. The page keeps the last few turns, answers in the question's language (English, Russian or Hebrew), and shows a collapsible "How I got this" trace under each answer.

`get_order_status` also returns defects grouped by type, so a follow-up such as "what type are its defects?" can be answered from that tool.

```powershell
python chat/server.py
```

Stop with Ctrl+C in that window.

Acceptance criteria:

- [ ] http://127.0.0.1:7777 loads in a browser.
- [ ] A question about an order calls `get_order_status`, and the answer matches the database.
- [ ] A question about a procedure calls `search_instructions` and names the instruction file.
- [ ] A follow-up uses the earlier order without the user repeating the id.
- [ ] The same questions in Russian and Hebrew are answered in that language, and Hebrew is right-to-left.
- [ ] An off-topic question says that nothing relevant was found.
- [ ] "How I got this" shows the tool, its arguments, the JSON result, and the model and time.

## Step 5: NGINX in front of the chat (dashboard later)

NGINX (`nginx:1.28.0-alpine`) publishes only `127.0.0.1:8088` and `127.0.0.1:8443`. HTTP redirects to HTTPS. The certificate is self-signed (`scripts/generate_certs.ps1`) and is not committed. NGINX proxies to the chat on the Windows host (`host.docker.internal:7777`). The employee chat is open. `/admin`, `/dashboards`, `/logs` and their APIs ask for a password (basic auth; the password is `ADMIN_PASSWORD` in `.env`). The chat app checks that same password, so opening those pages on http://127.0.0.1:7777 is not a way around NGINX.

The chat page has three columns: Dashboards and Logs on the left, the conversation in the middle, admin settings on the right. Dashboards is built when you click it (production numbers from the database, assistant numbers from `logs/events.log`). Logs shows the latest events and can download the whole file. Both HTML and Excel downloads are generated on the server. The HTML file is self-contained (inline SVG, no CDN). The workbook uses native Excel charts.

One event is one line in `logs/events.log`: time with timezone, level, component, event name, then `key=value` details. The file rotates by size. Questions are cut to 200 characters. Passwords are not written.

Double-click `start-chat.bat`. It opens https://localhost:8443. http://127.0.0.1:7777 still works for debugging. `stop-chat.bat` stops the chat and NGINX. `stop-chat.bat all` also stops the database container.

```powershell
powershell -ExecutionPolicy Bypass -File scripts\smoke_proxy.ps1
```

Acceptance criteria:

- [ ] http://127.0.0.1:8088 redirects to https://localhost:8443.
- [ ] https://localhost:8443 shows the chat, and a question is answered through the proxy.
- [ ] https://localhost:8443/admin asks for the admin password. Without it, `/api/settings` returns 401.
- [ ] http://127.0.0.1:7777 still opens the chat directly.
- [ ] `logs/nginx/access.log` records the requests.
- [ ] https://localhost:8443/dashboards and /logs ask for the admin password. The same URLs on port 7777 do too. The employee chat stays open.
- [ ] Dashboards shows production KPIs and, after a few questions, assistant stats. Download HTML works offline. Download Excel opens with editable charts.
- [ ] Logs shows recent events and Download saves `events.txt` in time order. `logs/events.log` has one event per line and does not contain the admin password.
